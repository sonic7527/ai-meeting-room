# 由 Codex 主持 AI 會議

使用者已指定：以後說「開會」可由目前 Codex 對話主持，沿用 CC 做法。主持是協調討論；最後決策由使用者拍板。主持本身不等於 `lead`（可改程式的主審）；使用者要 GPT 接手改專案時，照「使用者叫改就直接改」一節做。

## 主持執行準則（比照 CC，以成果推進）

這些是每次主持的工作規則，不是只供閱讀的心得。主持負責讓已授權工作往目標前進，不成為每個步驟的額外關卡。

- **沿用最新授權與現行狀態。** 派工前核對最新使用者指示、原 owner、已完成與正在執行的工作；後來指示明確改變範圍時，同步更新私人 state 與仍在用的自動化提示，註明舊限制被哪個指示取代。定時重播的舊提示、舊版本及「尚未放行」標記不能蓋過新指示。已授權的同件工作不反覆問許可，也不要求使用者照抄指定句型；真有歧義時只問尚缺的具體範圍。
- **按可交付成果分工，維持單一 owner。** 每項工作一次說清目標、輸入、範圍、產物、驗收證據及失敗停止條件；讓原負責席位在該範圍內做完。能獨立進行的實作、核帳或審查可由現有席位並行，受限資源維持既定串行。不要拆成一串都要等主持放行的微任務，也不因換室、換主持或額度事件重做已有成果。
- **集中驗收，避免邊看邊新增關卡。** 先定本階段真正影響正確性、成本或下一步的驗收清單；實作者交證據，審查席集中核對，主持處理分歧與必要門檻。能合併的缺口一次說完，只有新證據揭露實質問題才追加。已核版本與已足證分支不重複檢查、重跑；格式或非阻斷細節記為待修，不讓全場停等。測試數、SHA匹配或文件完成都不代替目標本身的結果驗收。
- **交付後立即接續下一個可執行步驟。** 區分實際阻斷、可採合理保守預設、可稍後處理三種情況。依結果決定下一個最小、能辨別原因的改動，不盲加矩陣；一個候選失敗不等於研究結束，草稿有局部缺陷也不必阻斷其他已授權工作。不可把讀取／保存同一狀態、重複解釋流程或道歉當成工作推進。
- **已啟動的作業不空轉干預。** 確認啟動、owner、產物路徑、預計完成時間及停止條件後，以既定有界等待或已授權排程接收結果；沒有新證據不重催、不重派、不重啟，也不拿過時限制中斷。主對話僅報重要交付、實際故障或真正需使用者決定的事；逐則轉述和無變化報告保持安靜。
- **工具拒絕精確處理，不把流程問題說成任務危險。** 記錄實際被拒的動作、原文理由及訊息有沒有送出；不要將單一拒絕擴張成所有研究禁止，也不要憑拒絕推論離線回測會下真單。完成不受影響的工作。若新使用者指示或可核實證據確實補足拒絕原因，再按新事實走正式審核；不能原樣重試、改提示偽造批准、換席代跑或間接繞過。仍需使用者處理時，一次交出具體可批准項目與真正卡點，不讓各席反覆辯論、重做文件或要求重講相同授權。
- **退出與學習不等於重新接任。** 使用者要求交接或停止主持時，保全狀態、發交接、停止派工及輪詢，刪除自己的主持 heartbeat；交接本身不等於停止執行中作業或散會。後續觀察、比較或修改技能只能依該次要求只讀或編修，不恢復主持、不更改接任者流程。收到接任確認才說接任完成。

自查：本次介入是否帶來新產物、解決實際阻斷或明確下一步？是否重問授權、重派原 owner、重驗已足證分支，或在沒有新資訊時仍發長篇？若只是重複，停止發言並讓現有工作繼續。不能用「讀完技能」或「寫了紀錄」宣稱已改善，要以後續執行是否少了無效等待、是否產生可驗交付判斷。

## 找到正確會議室

程式依序找 `$AI_MEETING_ROOM_DIR`、`~/ai-meeting-room`。新會議預設本機 `http://127.0.0.1:7720`，用 `start_bg.ps1` 背景啟動；不使用 `-Restart`，除非已確認沒有進行中的會議。

遠端位址從使用者當次提供的網址、`MEETING_URL`，或私人設定 `~/.ai-meeting-hosts.json`（以 desktop 等名稱對應 URL）取得。不要把私人主機網址或現行會議 id 放進公開技能。使用者提到桌機、CC 正在主持或繼續既有會議時，先讀正確主機的 `/api/rooms`，核對標題、專案、closed；不要因本機清單空白就另開一場。沒有遠端位址時先找既有本機設定或向使用者確認。

## 開新會議

使用目前專案（git 根目錄，否則 cwd），從對話整理 title、topic、限制與希望產出，lang=zh-TW，mode=discuss（檢查程式時 review），lead=""。沒有可推斷的題目時先問題目。沿用上次模型，不自行換模型與思考深度。

讀 `/api/agents` 確認可用席位；使用者明說邀誰就只邀誰，未指定則沿用既有開會技能的預設：空席開場，在網頁選擇邀請。不要把 installed/signed_in 當成實際入席成功；檢查建立回傳及後續訊息。使用者指定加入某會議或邀 AI 即授權該場會議的發言與邀請；單純查看、查詢或參考做法不授權發言。

用 UTF-8 無 BOM 暫存 JSON，執行 `python -X utf8 <會議室>/open_meeting.py <設定檔>` 建立並開瀏覽器；只支援本機。遠端會議則對選定 base 的 `/api/rooms` POST 同樣設定，再開回傳 id 的網址。邀請使用 POST `/api/rooms/<id>/invite` body `{"seat":"Claude"}`。新會議**預設開自主模式**：`open_meeting.py` 沒寫 `auto` 會自動帶 `true`；直接 POST `/api/rooms`（遠端）時設定要自己寫 `"auto": true`。只有使用者明說不要自主才寫 `false`；開完確認回傳 `"auto": true`，漏了就 POST `/api/rooms/<id>/auto` 帶 `{"on": true}`。使用者沒有要求改專案時，不指派程式修改權。

## 主持循環（Codex 遠端操作）

搭配本技能 `scripts/meeting.py`，標準 Python 3，無額外依賴。每次明確指定 `--base`，id 以原始中文參數傳入，工具負責 URL 編碼。

```
python -X utf8 <技能>/scripts/meeting.py --base http://127.0.0.1:7720 rooms
python -X utf8 <技能>/scripts/meeting.py --base <base> read <id> --after 0
python -X utf8 <技能>/scripts/meeting.py --base <base> say <id> --file <UTF8發言檔>
python -X utf8 <技能>/scripts/meeting.py --base <base> watch <id> --after <last_seq> --seconds 45
```

接續會議先讀私人交接快照及保存游標後的增量；只有沒有交接或游標時才首次分頁讀完整上下文。接著保存 last_seq，只讀增量；保留證據訊息編號。發言明確標成「【Codex主持】」，不冒充站長、CC、後台或其他 AI。新版 API 以 who=Codex主持 區分站長；舊版忽略 who 時正文仍保留身分。不要冒用其他參與者的 who。

整理議程與驗收標準，@具體席位分工；發現分歧要求證據和反例；區分已驗證、推測、待決。@席位是會議內建機制，無需另開 Codex 聊天或建立本工具的子代理。收到成果要檢查證據；誤判需在會議更正並引用原訊息。整理共識、分歧、成果檔和待使用者決定的事。

遠端手機連線時，命令輸出過密可能塞滿桌面程式的待傳送佇列而中斷連線。`read`／`watch` 預設每頁最多 3072 個 UTF-8 位元組，單行輸出；不要把完整逐字稿、長文件或大量日誌一次印到終端，也不要只依賴工具的 `max_output_tokens`，因為截斷前可能已傳送大量輸出事件。診斷時在程序內先篩選、彙總，再輸出少量結果。

API 連線、權限、逾時及無效回覆一律只回一行中文錯誤，不輸出堆疊、網址查詢參數或原始回應，也不自動重送。若遇本機權限限制 10013，使用工具正式的提權審核流程；不可改網路設定或另開背景服務繞過。呼叫其他診斷命令時也先在程序內收集、篩選輸出，避免未捕捉的錯誤堆疊再次造成輸出突發。

分頁回傳 `has_more`、`last_seq`、`next_offset`、`latest_seq`。`last_seq` 只到最後完整讀完的訊息；`latest_seq` 是伺服器最新序號，不可當成已讀游標。只要 `has_more=true`，用上頁的 `last_seq` 與 `next_offset` 接續：

```
python -X utf8 <技能>/scripts/meeting.py --base <base> read <id> --after <last_seq> --offset <next_offset>
```

`text_complete=false` 表示該則長訊息尚未讀完；接續片段與前段組合後才可判讀或派工。每次確認游標有前進；若附件或欄位過大，工具會明確報錯，改用 `snapshot` 保存完整紀錄，再分段讀本機檔案，不可跳到 `latest_seq`。完整快照不要直接輸出到終端。

watch 的等待預算最多 45 秒，單次請求逾時不得超過剩餘預算，預算耗盡後不再新增請求；等待所有新發言（主持需掌握各席成果）；用 after 游標接續，避免重複轉述或漏掉未點名發言。不要開無限背景監看後就宣稱能自行醒來；目前回合內以有界等待推進，離開回合前如需未來喚醒，須用可用的正式排程工具並核對使用者意圖。不可假稱有永久背景主持。

## 與 CC 交接、接續主持

使用者要求交接、額度不足換主持或接續既有會議時，先讀 [共用主持交接協議](references/host-handoff.md)。以共用 room id 的完整訊息為依據，發布「主持交接」與「接任確認」，保留最後讀取序號、原始使用者指示、唯一負責席位及待驗事項；不得因換主持重跑工作。

私人快照：`python -X utf8 <技能>/scripts/meeting.py --base <base> snapshot <id> --out <私人資料夾>`。先讀快照，再補讀游標後的現場訊息；快照不會自動同步。

## 使用者叫改就直接改

使用者在會議或主持對話說「你改」「後台改」「GPT 接管」「讓 GPT 改」，或把具體修改交給 Codex，就是授權在該範圍修改專案與本機 git 提交。立即沿用授權執行，不要求再說「指定主審」等句型、不反覆確認；主持可同時負責實作，不因「只是主持」停在唯讀。

依實際執行者選擇：

1. **後台 Codex 對話直接改（優先）**：先確認會議 `project` 與這個聊天的可寫範圍；已可寫就直接修改，不必切換會議主審或重啟席位。工作目錄不同不等於不能寫。工具需要額外權限時走正式權限審核，不能只憑目錄或主持角色宣告無權限。本機 API 若遇 WinError 10013，也先走正式審核，不重啟服務。
2. **由會議內 GPT 實作**：使用者要會議席位動手，或需要改由該席位承接時，先核對該場 `lead`、`direct`、`worktree` 及現有 owner。GPT 已是主審就直接做；只有確實需要變更角色才呼叫 `meeting.py --base <base> lead <id> --seat GPT`（第二席用 `GPT2`）。切主審會重啟該場在席 AI，須避開正在改檔或算圖的工作，不能為了拿權限中斷它們。`lead_direct` 開啟時可直接改原專案，否則在副本改，依該場實際 meta 判斷，不套用舊 README。

動手規則：

- 先讀專案 CLAUDE.md、AGENTS.md，沿用最新使用者授權及該專案的提交、推送與部署要求；已授權的動作不重問。單純叫改檔不自行擴張成未授權的部署、刪除、金鑰或正式環境操作。
- 同批檔案只有一位 owner。動手前在目標會議簡短交代範圍，完成後交檔案、差異與實際驗證；不重做前任已完成的成果。後台改檔可能觸發「原專案有變動」警告，先核對是否為已授權改動，不當成寫入失敗或直接還原。
- 以檔案內容、必要執行結果及 git 提交確認成功，不以「installed／seated／主審」代替實測。
- 權限審核拒絕後不換席位、換工具或改路徑繞過同一拒絕；完成不受影響部分，精確說明被拒動作與尚缺條件。
- 另開測試必用獨立專案及 room id，修改、發言、主審切換和散會僅限測試場；不重啟服務、不變更進行中會議。使用者取消測試時只結束該測試，保留驗證與逐字稿。

主持繼續沿用本技能既有準則：按成果分工、單一 owner、集中驗收、交付即接續、不重驗已足證工作，主對話只回報重要交付與真正卡點。修改技能不代表接任、派工或操作目前會議。

## 散會與成果

使用者同意散會後 POST `/api/rooms/<id>/close`。讀取匯出的 transcript.md，向使用者回報各方重點、共識與未決事項。操作原始專案、推送、部署、刪除仍需符合當次授權。

有結論的會議按既有 `~/ai-meeting-room/skills/開會/SKILL.md` 第 7 節：先把實際採用素材、程式保存進正式專案，確認可重做，再把這場淘汰素材與 rooms/seats 移入回收筒，保留逐字稿、紀錄與定稿。未散會或待續的會議不清理。不自動永久刪除。

## 手機遠端的執行方式

`rooms` 也採分頁，讀取 `rooms` 陣列，`has_more=true` 時以 `rooms --start <next_start>` 接續；不可因第一頁沒有目標就新開會議。`rooms`、`read`、`watch` 共用預設 3072 位元組上限（含換行），可用 `--max-bytes` 調整至 2048–12000。`say` 只回傳 `sent` 與 `seq`，不重複回傳發言全文。發言收件序號不是已讀游標，不可跳過期間其他席位的新訊息。

每回合只進行一個有界等待，不把多輪 watch、分頁或終端輸出串進同一個長時間工具呼叫。每頁讀完再決定下一頁；等待空結果不重發催促訊息。主持紀錄與附件留本機，只將必要文字分頁帶回對話；影片與大圖不因輪詢自動顯示到手機。前台只報新交付、實際下一步與需決定的卡點。

遠端連線變紅或工具失敗時，保留最後完整游標，重新連線後先核對房間與已送訊息，再接續；發言結果不明時不可自動重送。若已有其他主持依使用者指示接手，修技能期間維持其派工，不能另立第二位排程者。

本技能只管理會議操作，不以結束 ChatGPT／Codex 程序、重新啟動桌面版、修改配對或網路設定來修復遠端。技能更新透過安裝腳本熱更新，再重讀本檔即可；不得把短暫未斷線宣稱為傳輸層已修好。
